## Databases and AFFiNE research

The [research report](ZILLION-AFFINE-RESEARCH.md) records the pinned AFFiNE and REA sources, exact REA command/evidence, licenses and architectural findings. REA analyzed the real database package and produced a graph of 535 nodes and 752 edges. AFFiNE source/assets were not copied into this implementation.

Databases persist bases, typed fields, record content, saved views and relation edges. Primitive types include text, number, date, checkbox, select/multi-select and person. Compatible type changes convert existing values and filter operands atomically; incompatible values or saved views reject the change without modifying data. Relation fields remain structural. Table/Kanban/calendar views, filters, sorting, field visibility and page content share the same records. Paired relations enforce one/many cardinality, ownership, reciprocal updates and deletion semantics in PostgreSQL.

The implementation transfers AFFiNE’s separation of records/properties/views. It does not implement or claim AFFiNE’s canvas, CRDT, collaborative or offline synchronization system.

## Calendar and smart properties

Calendar views save their own start Date property and optional inclusive end Date property, render month/week/agenda layouts, retain undated pages and offer keyboard date movement as well as dragging. Moving a database range preserves duration, unrelated properties and page content; `expected_updated` rejects competing edits. Hidden card properties stay hidden. New-property shortcuts expose Date, Tags and Owner, with owner choices restricted to the current account and owned workspace principals.

Saved filters combine direct conditions and one bounded level of all/any groups. Date operators include strict before/after, inclusive bounds and today/tomorrow/this-week/this-month/next-seven-days/overdue windows. Tag and relation membership is exact; `Art` never matches `Cart`. Config parsing defaults old saved views safely. Date bindings cannot be deleted or changed to an incompatible type while a saved Calendar uses them; reversed ranges and foreign owner/relation operands reject atomically.

The dedicated Calendar combines native/ICS/module sources with the owned `calendarFeed?today=YYYY-MM-DD` database contract. Its source IDs distinguish saved views; it opens original records rather than editing their dates through native event APIs. Civil database days become local all-day intervals with an exclusive next-day end, including across daylight-saving transitions. Multi-calendar/category selections distinguish all from none; search, source, type, bounds, upcoming, tag and owner filters share one evaluator with mini-calendar indicators. Native drag/resize uses a dates-only endpoint to preserve unrelated event properties.

Direct Calendar loads resolve the installed Databases manifest before querying its registered contract. Development uses the host's sibling source loader, preserving one copy of the shared providers; production uses federation. Failed loads offer retry, and late results from replaced modules are ignored. Native event edits send the revision loaded by the editor; the server rejects stale changes while dates-only moves preserve concurrent metadata edits.

Interaction references were checked against [Notion calendars](https://www.notion.com/help/calendars), [views and filters](https://www.notion.com/help/views-filters-and-sorts), [property types](https://www.notion.com/help/database-properties) and the [filter API](https://developers.notion.com/reference/filter-data-source-entries). This implementation uses its own components and contracts. Database Date values currently represent civil days; timed appointments use native Calendar events. No new schema migration was needed for these JSON property/view extensions.

English, Malay, Simplified Chinese and Traditional Chinese cover new copy. Original LifeForge attribution remains visible in authentication and notices. Desktop and 390px layouts were checked, with horizontal table/board scrolling confined to their content areas. Collapsed mobile navigation is hidden from keyboard focus; collapsed desktop buttons retain names and keyboard activation.

## Migration and remaining limits

[Migration instructions](ZILLION-POCKETBASE-MIGRATION.md) document offline PocketBase SQLite/snapshot input, mandatory owner mapping, private reports, relation/file/settings integrity checks, default dry-run, guarded isolated apply, idempotent journals and rollback. Unknown production fields block until explicitly mapped. Rollback refuses edited rows/files, changed password hashes and newly dependent records. Production backups, the real profile and a production switch were not used.

External AI, OAuth, maps and other providers need configured credentials and were not called with assumed keys. Code Time’s local authenticated endpoint works; an external editor integration still needs owner configuration. CLI/Codex/OpenClaw automation requires a running configured worker and the runtime's own authentication; broad Wallet/Calendar/Todo mutation access, recursive agent delegation and automatic provider-invoice reconciliation are not implemented. Cost estimates and workspace reservations do not enforce provider-side billing caps. Documents, record bodies and Notes use the shared block editor. Old Markdown source stays literal until explicitly edited; automatic Markdown import/rendering is not implemented. Markdown export is readable text and does not preserve page/block identity. Full upstream parity, collaboration/CRDT sync, offline sync, rollups/formulas, publishing permissions and vault/plugin compatibility are not implemented. Docker is absent on this Mac, so container execution remains unverified. Global ESLint debt, the Calendar dependency warning and bundle-size warnings remain disclosed above; passing builds/tests do not establish that every possible bug has been eliminated.
