## Architecture transferred

Zillion OS adopts the separation of database metadata, typed properties, record content and saved views. A single persisted record set supports table and Kanban views. Property values are validated server-side according to current field metadata. Each record is also a content page.

Zillion OS uses its existing Forge API and PostgreSQL/Drizzle instead of importing BlockSuite's document/CRDT runtime. Its reciprocal relationships are a separate implementation, not an AFFiNE compatibility claim. It does not claim AFFiNE collaboration, offline-first behavior, canvas editing or CRDT synchronization.

## Zillion OS relation semantics

- IDs are UUIDs. Every base, field, record, saved view and relation edge has an authenticated `owner_id`. Requests cannot supply their own owner. Every lookup and mutation checks the verified owner.
- Creating a relation field creates a paired reverse field in the target base in one transaction. Each direction independently has `one` or `many` cardinality, supporting one-to-one, one-to-many and many-to-many. Same-base relationships are supported; a record cannot link to itself.
- The edge table stores directed source-field/source-record/target-record links with foreign keys and uniqueness. Mutating a relation replaces that record's selected targets and its reciprocal edges atomically. Both field directions use the same ordered locks. A target already occupied under a `one` reverse cardinality is rejected with a conflict, not silently reassigned.
- Deleting a record removes all incident edges through foreign-key cascades; other records and their content survive. Deleting either relation field deletes its paired field and both sets of edges. Deleting a base cascades its records, fields and views and removes counterpart relation fields in other bases that target it. Primitive-field deletion removes associated JSON values and cleans view references.
- Primitive field types can change in the field editor. The existing base lock serializes record/view writes; the server checks every value and saved view before atomically updating metadata, values and converted equality-filter operands. Field/record IDs, page content, unrelated values, nulls and absent values survive. Numbers use a canonical reversible representation (`42`, `1.5`); whitespace, leading zeros, rounding and unsupported numeric text are rejected. Checkbox text must be exactly `true`/`false`; dates use valid `YYYY-MM-DD`; selections must match target options. Multi-select becomes a scalar only when empty or holding one option; several choices are rejected without clearing data. Relation fields cannot change into primitive fields or vice versa, preserving reciprocal definitions and edges.
- A type change retains sort/visibility references and uses the resulting value type for sorting. Equality-filter operands convert with the values, while multi-select equality keeps its scalar membership operand. Empty-string equality cannot cross between a scalar and multi-select because exact equality and membership differ; the user must choose an empty/nonempty filter first. Numeric comparisons cannot move to another type; contains requires a text/selection target; a Kanban group must remain select/checkbox. Incompatible data or saved settings reject the entire transaction with the named record or view and instructions to edit it first. Option changes also validate existing values and saved selection filters.
- Saved view settings validate field IDs, filter values, sort directions and a suitable Kanban group field. Unknown field/record/base references are rejected.

## Block documents and second-brain relationships

Interaction research uses the official [Notion block-editing guide](https://www.notion.com/help/writing-and-editing-basics), [Notion links/backlinks guide](https://www.notion.com/help/create-links-and-backlinks), [Outline navigation guide](https://docs.getoutline.com/s/guide/doc/navigation-Nxnr2lWbck), [Obsidian internal links guide](https://obsidian.md/help/links) and [Obsidian graph guide](https://obsidian.md/help/plugins/graph). ZillionOS implements these interaction patterns independently. The shared editor uses Tiptap 3.31.4; the graph uses d3-force 3.0.0. No Notion, Outline or Obsidian source/assets were imported.

- Documents, record bodies and Notes use a versioned `zillion:blocks:v1` JSON envelope inside their existing text fields. The pure `@lifeforge/blocks` model is shared between UI and API. The server validates node grammar, unique block UUIDs, size/depth limits, safe links, supported numbering styles and owned page references. Old plain text stays unchanged until the user edits/saves it; old Markdown syntax is shown literally. Malformed block envelopes are rejected rather than silently reset.
- Supported blocks are text, headings 1–3, bullet/numbered lists, nested checklists, quotes, code and dividers. Formatting includes bold, italic and inline code. Blocks can be moved, duplicated and deleted; duplicates receive new UUIDs. Undo/redo uses editor history. Slash/block menus and an owned-page picker support creation and linking. Markdown export produces readable text; it is not a lossless identity-preserving backup or an import/round-trip feature.
- A standalone document has a title, body, optional parent and integer revision. Owner-scoped hierarchy locks prevent concurrent cycles, and updates/deletes require the expected revision. Removing a parent retains its children at the top level and increments their revisions. Record/note content uses expected timestamps, with monotonic updates to make competing writes conflict even within one clock tick. Navigation guards protect pending drafts.
- Page identity is `kind:UUID`, with document/record/note kinds. Saving an unambiguous `[[Title|alias]]` in a block document replaces it with a stable inline reference; subsequent renames retain the relation. The picker explicitly chooses among duplicate titles. Code is excluded from wiki linking. New foreign/missing IDs are rejected. Previously saved links to deleted pages retain their visible text and appear unavailable; they create no phantom graph nodes.
- Backlinks and inline edges are derived from current persisted bodies, avoiding a second copy of their state. Existing reciprocal database relations and document parents also appear in the graph. Additional labeled, undirected connections persist in `knowledge_links`: canonical keys and a unique owner/key pair deduplicate opposite-direction requests. Typed endpoint foreign keys clean manual links when a target disappears; other content survives. Forced owner policies cover both new tables.
- Graph views support global and local breadth-limited neighborhoods (depth 1–3), text/type/orphan filters, accessible page lists, keyboard selection/opening, pan/zoom/fit and node dragging. The force engine stops on unmount and respects reduced motion, including drag interactions. It is a personal workspace graph, not a collaboration or Obsidian vault compatibility layer.
- Relation editors keep a draft baseline. The server checks that baseline after acquiring the shared reciprocal lock and rejects a stale replacement; the UI offers a reload instead of silently overwriting an opposite-direction change. Opening a record in the same base preserves the selected saved view.

Document editing and graph behavior are covered by the [verification report](ZILLION-VERIFICATION.md). AFFiNE canvas/CRDT synchronization, Outline publishing/collections permissions, Notion formulas/rollups and full-text block search, and Obsidian vault/plugin compatibility remain outside this implementation.

Owner isolation is verified through route lookups and database row policies using independent synthetic owners.

The complete updated test inventory and browser scenarios are in the verification report.
